WHY THIS PROJECT

An approval is the beginning.

A payment touches different institutions, messages, and balances. This simulator makes those changes visible so you can explain what happened, identify a failure, and distinguish a reserved amount from money that has settled.

Trace

Who sends what?

Follow the request to the issuer and the decision back to the payer.

Compare

Which balance changes?

Separate available funds, authorization holds, clearing obligations, and merchant proceeds.

Explain

What happens on retry?

Inspect duplicate handling, conflicting requests, declines, and participant faults.

SIX PARTICIPANTS

A request travels out. A decision returns.

The local application launches six real Python participant processes. The supervisor delivers queued messages while the browser displays the shared classroom session.

1

Payer

Starts the purchase and receives its outcome.

2

Merchant / POS

Submits the purchase and requests capture.

3

Gateway

Processes and forwards the merchant request.

4

Acquirer

Represents the merchant’s side of the payment.

5

Network

Routes the fictional Visa/Mastercard message.

6

Issuer

Checks the account and applies the teaching rules.

A $50 PAYMENT · $500 STARTING BALANCE

Watch the balances tell the story.

Authorization

A $50 hold leaves $500 posted and $450 available. Merchant proceeds are $0.

Capture

The merchant records its collection instruction. A capture is a distinct step after authorization.

Clearing

In this teaching model, the payer debit posts: $450 posted, the hold disappears, and $50 is due to the merchant.

Settlement

The obligation is settled and the merchant receives $48.75 net, after $1.25 in illustrative issuer, network, and processing fees.

These are simplified dual-message, debit-style teaching conventions. Real payment products and schemes vary.

GUIDED EXPLORATION

Run it. Observe it. Explain it.

Use the checklist to explore the reference implementation. It is unscored; project assessment requirements come from your individual assignment.

  1. Walk an approved purchase

    Select Guided mode, the approved scenario, and $50. Use Next Message to trace the request and response. At AUTHORIZED, explain posted versus available balance.

  2. Finish the lifecycle

    Capture the payment, advance messages, Clear Batch, advance again, then settle the batch. Explain each balance change before clicking the next action.

  3. Inspect a decline

    Choose a low-balance or inactive-account scenario. Read the reason and confirm that no successful payment proceeds are created.

  4. Retry and compare

    Retry an existing request. Explain why a matching retry must not create a second financial effect. Compare with a conflicting request.

  5. Inspect the evidence

    Read the event trace, participant details, and tests. Identify a limitation and the additional controls a production system would require.

START IN A FEW MINUTES

Your computer is the classroom lab.

Download and extract the complete source package. Install Python 3.9 or later and use a recent browser. No paid service, payment account, or model API is required.

macOS / Linux

cd project-0-payment-rails
python3 start.py

Windows

cd project-0-payment-rails
py -3 start.py

Open http://127.0.0.1:8010. Keep the terminal running; Ctrl+C stops all participants.

Verify the implementation

python3 -m unittest discover -s tests -v

The complete test suite includes guide packaging checks and requires Node 24. Running the Python simulator itself does not require Node.

Optional Docker launch

docker build -t payment-rails-live .
docker run --rm --init \
  -p 127.0.0.1:8010:8010 payment-rails-live
Troubleshooting and session behavior

If the port is occupied, use python3 start.py --port 8020. If the browser does not open, visit the printed address. Start through the launcher so the dashboard APIs are available.

Refresh reconnects to the running shared session. Reset, stopping, or restarting clears balances and history. A participant fault pauses the demonstration; inspect the fault and use Reset.

What would a production system need?

The reference uses fictional tokens and funds, deterministic rules, local queues, and in-memory state. It does not implement a durable ledger, crash recovery, real network access, refunds, disputes, or partial capture. The technical design guide discusses durable messaging and cloud evolution.
